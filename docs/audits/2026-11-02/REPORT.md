# Hermes Agent Mobile audit — 2 November 2026

The app needs a **1.0.1 correctness release before expanding integrations**. Four diagnostic probes reproduced defects in connection isolation, compatibility conversation history, durable decisions and cron validation. The feature audit also found substantial supported-API functionality that the native UI does not expose. A completed milestone checklist and passing smoke tests did not cover these interleavings and wire-history cases.

App reviewed: **1.0.0 / 50030c00034d2c496a2c4b57c821e4f1b0de1d7b**. Upstream targets: [latest stable v0.22.5](https://github.com/NousResearch/hermes-agent/releases/tag/v0.22.5) at `bf0203a794a07aac3ff764972ab9087baa4e4f4e`, and main at [`0aab6dc`](https://github.com/NousResearch/hermes-agent/tree/0aab6dcf8b7869acbab06507c34881b53036c09a). The audit inspected pinned public source and current official documentation. No live Hermes deployment or provider credentials were supplied, so these targets are reference contracts rather than a claim about the owner's installed server. Only audit files and a read-only checker were added locally; product behavior and published releases were not changed.

HAM-A001 · **P1 — An in-flight run control can move to a different connection**. [HermesViewModel.kt:75](https://github.com/DionCroft/hermes-agent-android/blob/50030c00034d2c496a2c4b57c821e4f1b0de1d7b/app/src/main/java/org/hermesmobile/app/ui/HermesViewModel.kt#L75), [HermesViewModel.kt:303](https://github.com/DionCroft/hermes-agent-android/blob/50030c00034d2c496a2c4b57c821e4f1b0de1d7b/app/src/main/java/org/hermesmobile/app/ui/HermesViewModel.kt#L303), [HermesViewModel.kt:340](https://github.com/DionCroft/hermes-agent-android/blob/50030c00034d2c496a2c4b57c821e4f1b0de1d7b/app/src/main/java/org/hermesmobile/app/ui/HermesViewModel.kt#L340)

Hold the status read for an unknown-run acknowledgement on A, save/test connection B, then release the A response. The resolve-unknown POST goes to B with B credentials but A run/admission identity; a subsequent B status response is written into the A conversation. The probe uses cloned run identities, representing overlapping/cloned deployments. No A bearer token is sent to B.

Required result: The complete operation stays bound to the original immutable connection/profile and receipt identity; unrelated connection changes cannot redirect it. Fix direction: Pin connection/client/scope for the whole operation, gate connection changes while controls are busy, and reject stale asynchronous context writes. Audit all select/detail/reconcile paths under the same rule. Reproduction: `changingConnectionDuringUnknownAcknowledgementSendsControlToTheNewProfile`.

HAM-A002 · **P1 — Compatibility-mode follow-up requests lose assistant history**. [HermesViewModel.kt:238](https://github.com/DionCroft/hermes-agent-android/blob/50030c00034d2c496a2c4b57c821e4f1b0de1d7b/app/src/main/java/org/hermesmobile/app/ui/HermesViewModel.kt#L238), [HermesStreamParser.kt:30](https://github.com/DionCroft/hermes-agent-android/blob/50030c00034d2c496a2c4b57c821e4f1b0de1d7b/app/src/main/java/org/hermesmobile/app/network/HermesStreamParser.kt#L30)

Complete one OpenAI-compatible streaming answer, then send a follow-up referring to that answer. The assistant answer is saved with response_finished, but the next HTTP request includes only the two user messages. The history filter retains assistant rows only when their status is completed.

Required result: A completed response remains eligible for conversational context without treating response completion as proof of server tool/run completion. Fix direction: Separate response/history eligibility from authoritative execution outcome. Preserve completed and policy-approved partial assistant text; test wire history over multiple compatibility turns. Reproduction: `compatibilityFollowUpActuallyOmitsThePreviousAssistantAnswer`.

HAM-A003 · **P2 — A delayed SSE prompt resets protected decision states**. [Models.kt:120](https://github.com/DionCroft/hermes-agent-android/blob/50030c00034d2c496a2c4b57c821e4f1b0de1d7b/app/src/main/java/org/hermesmobile/app/data/Models.kt#L120), [Models.kt:128](https://github.com/DionCroft/hermes-agent-android/blob/50030c00034d2c496a2c4b57c821e4f1b0de1d7b/app/src/main/java/org/hermesmobile/app/data/Models.kt#L128)

Persist an unknown or resolved control, then save a delayed stream update containing that same prompt. saveTurn unconditionally upserts the incoming pending row. Both unknown and resolved states become pending. replaceControls has protective merge logic, but the SSE path bypasses it.

Required result: GET snapshots and SSE events share a transactional, generation-aware monotonic state merge. Fix direction: Centralize control merging; preserve unknown/responding/resolved for the same generation except an explicitly authorized refresh transition. Retain exact server verification before decisions. This probe does not establish a server-side approval bypass. Reproduction: `delayedStreamPromptResurrectsUnknownAndResolvedControlRows`.

HAM-A004 · **P2 — Job prompt validation exceeds the upstream REST limit**. [JobProtocol.kt:11](https://github.com/DionCroft/hermes-agent-android/blob/50030c00034d2c496a2c4b57c821e4f1b0de1d7b/app/src/main/java/org/hermesmobile/app/network/JobProtocol.kt#L11), [JobOperationsRepository.kt:20](https://github.com/DionCroft/hermes-agent-android/blob/50030c00034d2c496a2c4b57c821e4f1b0de1d7b/app/src/main/java/org/hermesmobile/app/data/JobOperationsRepository.kt#L20)

Review/create a job with a 6000-character ASCII prompt. The mobile validator accepts it; both pinned upstream API implementations limit cron prompts to 5000. A matching HTTP-400 fixture causes an unknown receipt that blocks subsequent mutations pending human review.

Required result: Known supported limits are enforced before submission; documented definite pre-admission refusals are distinguishable from ambiguous delivery. Fix direction: Use the supported 5000-character contract unless a future negotiated limit says otherwise, provide localized validation feedback, and preserve structured refusal codes/Retry-After. Do not classify every arbitrary HTTP 400 as proof of no mutation. Reproduction: `jobPromptAcceptedByMobileButRejectedByServerIsRecordedAsUncertain`.


HAM-A004's server constraint is independently visible in [stable API source](https://github.com/NousResearch/hermes-agent/blob/bf0203a794a07aac3ff764972ab9087baa4e4f4e/gateway/platforms/api_server.py#L3776) and [main API source](https://github.com/NousResearch/hermes-agent/blob/0aab6dcf8b7869acbab06507c34881b53036c09a/gateway/platforms/api_server.py#L3282). Its HTTP probe uses the same refusal shape; it does not run a real Hermes instance. P1 means fix before broadening/recommending affected workflows; P2 means a significant reliability or contract issue. No P0 remote-code-execution or credential-exfiltration finding was established by this audit. The A001 fixture proves wrong-target operation/data flow; the encrypted URL/token pair itself remained intact.

The integration distinction matters: a configured Hermes backend can already use its chosen LLM provider, MCP tools, web/browser tools, memory and skills while serving a mobile conversation. Missing phone setup/status pages do **not** mean those server tools are unsupported. Native management is a separate requirement. The [bearer API](https://github.com/NousResearch/hermes-agent/blob/0aab6dcf8b7869acbab06507c34881b53036c09a/gateway/platforms/api_server.py) exposes a smaller external-client surface; the [dashboard](https://github.com/NousResearch/hermes-agent/blob/0aab6dcf8b7869acbab06507c34881b53036c09a/website/docs/user-guide/features/web-dashboard.md) has MCP/catalog, channels, webhooks, pairing, memory and provider-management routes under its own auth gate and profile selection. The stable dashboard docs also list these MCP routes. We must implement or bridge that management connection deliberately, with verified authentication, target profile and permissions. Reusing the existing bearer token against guessed dashboard paths is not an integration design.

The next release sequence should be concrete:

1. **1.0.1 — correctness.** Pin operation context, protect connection transitions and scope every asynchronous result; repair compatibility history while separating response and execution outcomes; unify GET/SSE decision merging; align cron limits and typed refusal handling. Convert all four diagnostic probes into tests that expect the fixed behavior. Cover switching/forgetting/Demo transitions, out-of-order control events, multi-turn compatibility, partial responses, known refusals and ambiguous acknowledgements. Preserve migrations and the existing no-auto-replay policy.
2. **1.1 — supported API parity.** Add an actual connection/capability/readiness screen; model/provider/session-lock controls; skills/toolset discovery; session fork; run steering; usage/effective runtime; tool-call IDs and subagent lifecycle; intentional conversation-memory keys; image input/output. Persist the exact request specification for idempotent replay when adding model/provider/image options. A model picker that changes replay bodies under an existing key is incomplete.
3. **1.2 — integration management and advanced automation.** Decide the separate dashboard/native auth or scoped upstream bridge first. Then add MCP/catalog and channel/webhook status, reviewed management actions, richer cron fields/results, and remote board/project/goal/heartbeat/loop monitoring. Start read-only. Do not send cron fields outside the verified REST whitelist and silently claim they were applied. Provider keys, terminal backends and agent execution remain on Hermes.

Keeping up needs repeatable checks rather than a one-time feature count. `scripts/check_hermes_contract.py` now resolves a release tag or main through the installed GitHub CLI, pins its commit, downloads the three routing modules through the supported GitHub API and parses them as Python AST without importing/executing them. It compares route registrations, static features, selected job constraints and editable fields to `upstream-baseline.json`, including the app's 24 used route shapes. It reports existing open findings separately. A zero exit means no tracked upstream drift affecting those shapes; it is **not** a clean bill of app health or live interoperability. Exit 2 requests mobile review; exit 3 means the check is incomplete. New endpoints/features still need human triage even with exit 0.

The checker was exercised online against v0.22.5 and main, and with five decision checks: unchanged stable; used route removed; unused route removed; changed job limit; removed used job field. Main has 44 registered route shapes versus 48 in stable (including conditional registrations). The four removed routes are the old browser-control register/WebSocket and artifact upload/download endpoints; none is used by the app. This is a concrete deprecation to avoid when implementing media/browser support. Static route counts do not measure feature parity and do not validate payload semantics or runtime permissions.

Example commands (manual, no recurring schedule was activated):

```powershell
python -B .\scripts\check_hermes_contract.py --ref latest --output E:\Temp\hermes-stable-drift.json
python -B .\scripts\check_hermes_contract.py --ref main --output E:\Temp\hermes-main-drift.json
```

The release gate should test the latest **supported stable** Hermes plus a prior supported version, using the real pinned server with a deterministic model/tool adapter and synthetic configuration. A main canary should run separately, with additions/removals assigned for review; it should not silently redefine supported production behavior. Re-run these checks before every mobile release and triage upstream releases on a regular cadence. Add contract fixtures tied to source commits, schema-change review, a capability matrix and explicit unsupported-feature UI. Instrumentation currently compiles in CI but runs locally; add minimum/current Android emulator jobs and representative ARM64/hardware checks. Add dependency update/advisory review, Gradle verification/locking policy and release provenance. This audit did not activate workflows, create public issues, connect external integrations or change provider configuration.

Verification performed here: **four isolated Android-16 diagnostic probes confirmed the current defects** using loopback MockWebServer/in-memory Room; instrumentation compilation succeeded; production dependency resolution succeeded; the OSV query returned complete responses for 150 resolved production Maven coordinates with **zero indexed advisory matches**. BOM/metadata components are included, so this is not an APK/native SBOM or a full vulnerability assessment. Build plugins, operating systems, native binaries and future/unindexed advisories are outside that result. Dependency and checker metadata are in the adjacent JSON files; generated raw logs are in ignored `artifacts/audit-2026-11-02/`. Diagnostic source is under `probes/`, outside normal test inputs, because its assertions intentionally describe the defects.

Existing protections worth retaining are trusted HTTPS, no credential-following redirects, atomic encrypted connection snapshots, profile-partitioned caches, fresh exact-prompt verification, individual once/deny controls, read-only background checks, non-destructive migrations, reviewed bounded task import and private production signing. These do not remove the need for the correctness fixes above.

Still unverified: a real v0.22.5/main Hermes runtime, representative live MCP integrations/provider routing, physical microphone/TTS, real launcher widget pin/resize, OEM background/reboot delivery, ARM64 hardware and target-API-37 runtime behavior. A001 also motivates additional stale job-detail/history/result tests; those broader paths are audit leads, not additional confirmed exploits. Portable signing-key recovery/restore and a complete SCA/SAST/provenance pipeline need operational evidence. The project currently has no scheduled upstream check, Dependabot/Renovate configuration or Gradle dependency-verification file. The manual checker added by this audit is the first reproducible maintenance step.

Distribution follow-up: the app has a source link but no native update check. Add a trusted stable-release/version notice or release-page handoff, and verify future production-signed upgrades preserve data. Keep signing-key recovery separate from temporary build caches; a successful local signing operation is not evidence of a portable recovery test.

Post-audit baseline verification also passed: 43 JVM unit cases, all 30 normal Android-16 device cases, lint, debug APK and instrumentation build. The temporary probe was removed from normal test inputs before that run. Passing the existing baseline alongside reproduced defects demonstrates the coverage gap; it does not close any finding.

Two design details should stay explicit during follow-up. Image input is documented on the bearer API now; generic document uploads and delivery of host-local generated files/audio need an actual supported media contract, especially after the old artifact routes disappear from main. A stable memory/conversation key should identify the intended logical channel independently of a rotating transcript session; do not create a new per-turn key or assume missing headers mean memory is leaking.

Additional race tests should include a late stop/status response arriving after a newer turn starts in the same conversation. Reconciliation must check run/receipt identity as well as profile before writing. That broader interleaving is a follow-up lead; the confirmed cross-connection reproduction remains HAM-A001.
