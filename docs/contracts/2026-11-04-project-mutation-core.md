# Stored project mutation core — 4 November 2026

This is internal development infrastructure after the reviewed project-read chunk. The app's project screen remains read-only until the forms, frozen approvals, shared-home receipt projection and explicit uncertainty review are wired in a subsequent chunk. No new project write button or public APK release is claimed here.

## Verified primary source

The official [mutation handlers](https://github.com/NousResearch/hermes-agent/blob/b200f5bc60e31588ba2cb60e288029c4a54ba5fa/tui_gateway/methods_projects.py), [typed parameters/results](https://github.com/NousResearch/hermes-agent/blob/b200f5bc60e31588ba2cb60e288029c4a54ba5fa/tui_gateway/contracts/projects_pets.py) and [project store](https://github.com/NousResearch/hermes-agent/blob/b200f5bc60e31588ba2cb60e288029c4a54ba5fa/hermes_cli/projects_db.py) were re-read as source. Their verified original-baseline source is unchanged for these contracts. Native authentication continues through `POST api/auth/ws-ticket` and a one-use gateway-purpose subprotocol ticket, preserving configured URL prefixes and the separate management bearer. Every typed call explicitly includes its reviewed profile. There is no arbitrary-RPC API, server-request opt-in, repository discovery, reconnect or mutation replay.

The core supports `projects.create`, `update`, `add_folder`, `remove_folder`, `set_primary`, `archive`/restore, `delete` and `set_active`/clear. Create always sends `use:false`; activation is a separate review. Update sends only supplied fields. Empty description is a saved empty string; empty icon/color/board reference clears those values, while omitted fields remain unchanged. Paths are passed to the host without Android filesystem resolution. Blank paths are refused because host normalization can otherwise turn them into its current directory. Host normalization, slug suffixes, first-folder primary selection and primary reassignment are host behavior, never an invented exact input-to-path proof.

`get_project` resolves an exact ID first and then a lowercase slug. Frozen requests require a current canonical target and reject a known other-project slug collision with that ID. Immediately before a write the core reads the complete bounded stored inventory and rechecks owner/home and the reviewed metadata. It checks the home around subsequent readback as well. The API supplies no transaction revision or conditional-write token; external changes between these operations remain a residual race. The future approval UI must describe that limit.

## One send, acknowledgement and observation

A typed immutable review retains private input only in memory. One durable claim precedes at most one mutation call. Names, descriptions, paths, raw arguments and canonical IDs are omitted from durable request/result summaries; those summaries retain action/field names, counts, booleans and appropriate ID hashes. Debug/error string rendering is redacted. No restart routine reconstructs or resends private arguments.

A successful typed response is recorded as acknowledged before profile checks and fresh configuration readback. Only an independently read configuration that agrees with the acknowledgement and reported requested effect becomes confirmed. In particular, `set_primary` can return a successful RPC while its underlying operation returned false; an unchanged primary never becomes confirmed. A nullable create result is an acknowledgement without an available project, not fabricated creation details. Normalized paths retain an explicit unverified input-to-path mapping flag. Neither a board reference nor an active-project pointer proves board existence, changed chat working directory, changes to project-directory contents or runtime adoption.

Matched code **5062** is the verified `_require_project` refusal before non-create/non-clear mutations. Create errors, code 5063, generic errors, lost sockets and malformed acknowledgements may occur after a write and remain unknown. A locally cancelled claim that has not reached the call is recorded as not sent; cancellation after entering the send retains uncertainty. Acknowledgement survives failed/cancelled readback. Nothing automatically repeats an unknown write or manufactures a replacement operation key.

## Shared-store durability and privacy

Room **11** adds an indexed `projectHome` fingerprint to management receipts, retaining original profile/resource ownership. The additive 10→11 migration keeps every prior receipt, state, request identity and unrelated app table. Legacy receipts have an empty home binding. New project claims require a valid verified-home fingerprint; other operation kinds keep an empty one. Same-home aliases share the pending barrier at the exact dashboard URL, independent of inference credential or management actor. Other reported homes and URL prefixes remain independent, alongside the existing profile/instance barriers.

Foreign settled history is filtered before the 100-row page limit. Pending work from the same store can be projected as a generic notice with private original metadata removed. Its internal fingerprint remains available solely to recheck visibility after a home change. A verified same-store review can remove an unknown local barrier after identity/profile reads; it neither contacts a mutation gateway nor determines the original server outcome. Sending work cannot be locally settled. Future UI integration must freeze this home binding, show the shared scope/effect, require explicit consent and prevent stale receipt views from widening it.
