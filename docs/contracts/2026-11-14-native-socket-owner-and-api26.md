## Exact existing connection and native process

`scripts/native_retirement_owner.py` accepts a separately selected native Owner.
The caller still verifies that it is the intended manager-owned SDK process.
The observer does not discover a replacement or trust an HTTP PID. It reads the
exact client socket's reverse established IPv4 loopback tuple in the current
kernel table, then requires that inode in the selected process's FD directory.
UID and network namespace must match; PID/start ticks/boot identity, endpoints
and the table inode are checked again. A same-port listener alone is insufficient.
The kernel documents the [TCP table fields](https://docs.kernel.org/networking/proc_net_tcp.html);
the Linux manuals define [process start ticks](https://man7.org/linux/man-pages/man5/proc_pid_stat.5.html)
and [socket inode FD links](https://man7.org/linux/man-pages/man5/proc_pid_fd.5.html).

Each observation has a one-second monotonic bound, bounded record sizes and at
most 4,096 inspected descriptors. It has no injectable proc root, network
request, subprocess, signal, credential read or write. Inaccessible/ambiguous
records, unaccepted connections, wrong identity/user/namespace, non-established
state or lost socket return unknown. It is deliberately Linux/IPv4 loopback
specific; unsupported states are not inferred healthy. The proc interface is
deprecated in favour of tcp_diag; availability is observed rather than assumed.

These samples are non-atomic and do not prove exclusive FD ownership, SDK role,
authentication, source identity or idle work. Those remain caller/guard checks.
The HTTP component retains its original socket and refuses reconnects, so a new
listener cannot silently inherit a request after a reset. Nothing here grants
permission to stop a service or treats an idle snapshot as a retirement permit.
