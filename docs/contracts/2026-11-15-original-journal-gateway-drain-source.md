## Controller contract

`NativeGatewayDrain` has no live CLI, stop/restart operation, thaw, cancellation,
marker refresh, recovery or replay entrypoint. It runs in a fresh isolated
Linux process with bytecode writes disabled and the reviewed SDK PM environment.
The caller supplies exact reviewed source inventories, private home, native
unit/configuration, socket, ledger inode/schema, fence preimage and controller
configuration. A released positive fence epoch is valid; an existing frozen
owner is never adopted. The reviewed schema must already exist, without
triggers or a pending owner-birth migration.

Preparation captures and rechecks full SDK/executor inventories. It neither
imports the SDK nor opens SQLite. The original forward authorization, deadline,
live journal owner, exact pending `gateway_drain` prefix, native operational
ancestry and native service/controller identity are checked repeatedly. The
dispatch claim is consumed once before the receipt, gateway exchanges, SQLite
connection, SDK imports or constructor. An already-present marker or replaced
ledger refuses before claim. After claim an uncertain effect remains unknown,
with the stage pending and a held receipt where persistence succeeds.

Gateway observations use fresh Unix connections bound to the original kernel
peer. Known busy replies may be observed again within fixed, separate
five-second startup and drain windows; receipt time counts. Unknown, expired,
foreign or late observations stop. There are at most 64 requests and two seconds
per exchange. Read retries are not mutation replay permission.

After an original ready/idle observation, the controller checks a read-only
schema and unused operation, installs the source-verifying SDK import gate and
constructs the actual SDK Ledger. SDK Python source is hash-verified and compiled
from reviewed bytes; unchecked bytecode, foreign SDK namespaces and unlisted
SDK-root modules are refused. Ordinary PM dependencies retain their separate
qualification boundary; no complete dependency claim is added here.

The intended success path calls the supported Ledger freeze once and checks
the next exact owned epoch. It creates a private temporary marker and publishes
with Linux `renameat2(RENAME_NOREPLACE)`, with authorization immediately before
publication. The exact SDK five-field payload binds action, UTC time, generated
principal, native boot/PID1 epoch and suppression flag. No existing matching
marker is accepted or refreshed; arrivals and failed temporary files remain.
There is no replacement fallback, automatic unlink or thaw. Final checks bind
the ledger, marker, honored SDK payload, inventories and native owners.

A potential result proves only a registered home was observed drained. It
explicitly leaves gateway/all-profile/worker admission and fleet readiness false.
The controller does not mark the journal stage verified or perform a service
action. Broader coordination, terminal proof and recovery remain separate gates.
