## A separately measured local race and bounded candidate fix

A fresh in-process local client instruments only its own projection selection
and native error classification. The same fresh projection advertises ready for
status, prepare and list (age 0.36-0.55 seconds). Prepare replies; the immediate
list connection gets Windows error 231, BUSY, with requestSubmitted=false.
No list request reaches the provider in that observed connection. This proves a
ready projection cannot reserve the next pipe connection. It does not establish
that the Pi's differently classified UNAVAILABLE has the same cause.

The candidate calls WaitNamedPipeW once before its single CreateFileW attempt,
using only the remaining original deadline. It never uses an infinite/default
wait, extends the request deadline, retries CreateFile, resends a frame or
restarts the listener. The caller SID check precedes waiting. Server PID, full
creation time, SID and session checks still precede every request write.
Submission uncertainty remains conservative after a failed write or lost reply.
Another caller can still win after availability, so a later BUSY is refused.

Microsoft documents [the finite availability wait and remaining connection race](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-waitnamedpipea)
and [named-pipe client connection behavior](https://learn.microsoft.com/en-us/windows/win32/ipc/named-pipe-client).
The implementation uses the Unicode W variant with an explicit native signature.
No stale/non-ready projection is upgraded to ready by this change.
