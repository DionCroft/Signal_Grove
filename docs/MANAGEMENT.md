# Hermes management connection

The inference API and dashboard are different listeners and authentication systems. Settings → Hermes management explicitly links a dashboard HTTPS URL to the selected saved API connection. Production requires HTTPS; debug HTTP is an explicit test setting. The API bearer token is never sent to management. Demo has no management backend.

1. Select a saved API connection. Enter the dashboard URL, including any deployment prefix.
2. Choose **Sign in using browser**. Complete the dashboard password/OAuth provider flow in the system browser, then return to the app. The server can present its own provider chooser.
3. Select a verified **Managed server profile**. The MCP surface lists configuration and offers reviewed connection tests, enable/disable and configuration removal for that explicit profile. Enabled configuration does not prove connectivity or credentials work.
4. **Refresh** re-verifies identity and the available profiles. **Renew sign-in** explicitly rotates the management session. If a refresh response is lost or rejected, sign in again; no mutation or refresh is automatically replayed.
5. **Forget this device’s management sign-in** removes its local tokens without changing the API connection. Removing the API credential also atomically removes its linked management session. Browser/server sessions are governed by the dashboard.

The browser flow uses Hermes’ RFC 8252 native authorization contract and S256 PKCE. The app binds an ephemeral socket only to device loopback 127.0.0.1, requires the expected Host and callback path, rejects duplicate/mismatched state and code parameters, and does not reflect codes in its response. The verifier and code remain in memory. Cancellation, connection changes and view-model disposal close the listener; the login expires after ten minutes. A killed app must start a new sign-in.

Token exchange and explicit renewal use JSON requests with no API bearer header or cookies. Authenticated reads use only the management access token. The app verifies `/api/auth/me` against the returned provider/user identity before accepting a sign-in. `/api/status` is not used as authentication proof. Requests retain URL prefixes, use TLS validation, refuse redirects and automatic connection retries, check Android LAN permission and bound response sizes. Saved access/refresh pairs and profile selection use Keystore encryption under the exact API credential scope. A later profile switch cannot attach an older login result to the new connection.

Restored sign-ins are labelled saved until manually verified. Server profile selection is explicit and constrained to the authenticated profile list; MCP requests always carry `?profile=...`. There is no inferred default profile or mapping from the API path. Configuration URLs, command arguments, environment values and credentials are excluded from the inventory display.

MCP connection tests, enable/disable and configuration removal are implemented with reviewed targets and durable uncertainty receipts. Typed server creation is also implemented. Reviewed catalog installation and native MCP OAuth setup are implemented in the sections below. It does not claim an HTTP substitute for CLI-only features or support bearer API admin routes that Hermes advertises as unavailable.

Contracts verified against stable v0.22.5 (`bf0203a794a07aac3ff764972ab9087baa4e4f4e`): [native authentication](https://github.com/NousResearch/hermes-agent/blob/bf0203a794a07aac3ff764972ab9087baa4e4f4e/hermes_cli/dashboard_auth/routes.py), [loopback code/PKCE lifetime](https://github.com/NousResearch/hermes-agent/blob/bf0203a794a07aac3ff764972ab9087baa4e4f4e/hermes_cli/dashboard_auth/native_flow.py), [profiles](https://github.com/NousResearch/hermes-agent/blob/bf0203a794a07aac3ff764972ab9087baa4e4f4e/hermes_cli/web_routers/profiles.py), [MCP](https://github.com/NousResearch/hermes-agent/blob/bf0203a794a07aac3ff764972ab9087baa4e4f4e/hermes_cli/web_routers/mcp.py), and [dashboard guide](https://hermes-agent.nousresearch.com/docs/user-guide/features/web-dashboard).

## Reviewed MCP controls

Each action review names the dashboard URL, explicit profile, authenticated actor, server and intended effect. Before writing, the client re-verifies identity and reads configuration. A changed source or enabled state requires a fresh review. Already-present desired configuration is reported as an observation without another write. Plugin/unknown-source configurations cannot be enabled or removed here; connection tests remain available. Names that cannot use the verified route are visibly unsupported.

Enable/disable sends only `enabled` and the matching `profile`; removal deletes configuration, not running processes. Changes affect new sessions or gateway reloads; existing work may continue. Connection testing can start the configured host process to list its tools. The probe result is separate from agent execution status. The result view reports the supplied tool count and up to 100 names, without persisting descriptions, schemas, environment values or server error text.

Schema 10 keeps management action receipts separately from chat caches. The receipt records the exact resource/actor/action and a redacted summary before the single request. It contains no management tokens, arbitrary secret payload or command arguments. One unresolved action blocks further changes for that exact canonical dashboard URL (including deployment prefix) and server profile, across all saved inference connections and native-account rotations. Process restart changes interrupted sends to unknown. No management action is automatically replayed, refreshed with another credential, or retargeted. A valid acknowledgement cannot be downgraded when later readback fails.

**Read current configuration** gives an observation without settling uncertain earlier work or claiming causality. **Review uncertainty** explicitly marks that local receipt reviewed; it does not resend or cancel server work. Changing server profiles keeps each resource’s uncertainty separate.

Schema 9 included the inference credential scope in the pending-resource key. That allowed a second saved connection to send another management mutation to the same dashboard/profile after a lost reply, or win a second concurrent claim. Schema 10 transactionally re-keys every historical management receipt using its stored dashboard URL and profile, including receipts whose original inference credential was removed. Original keys, inference ownership, actors, actions, payload summaries, timestamps and acknowledgement states stay intact. Startup recovery still changes interrupted sends to unknown.

Private history remains attached to its original inference connection. The history query excludes other connections’ settled receipts before applying its 100-row limit, so those receipts cannot displace the current owner’s history. Sending and unknown work remain shared and take priority. Another connection receives only a generic pending-work notice, without the original actor, operation, target, request, result, time or inference-scope hash. The same privacy projection is applied when displaying rows during a connection switch. A request still sending has no local-clear action. After verifying the current management identity/profile, **Review uncertainty** can explicitly mark an unknown receipt from another or removed connection reviewed locally. Canceling the review leaves the block in place. This does not establish success, cancel host work, replay anything, or reveal the other connection’s history. More than 100 historical pending receipts remain blocked and become reviewable as earlier visible receipts are reviewed.

This is a device-local guard for the exact configured URL and profile. It does not serialize other devices or external dashboard/CLI actions, establish backend idempotency, or identify different hostnames/reverse-proxy aliases as the same server. OAuth flow reads, browser handoffs and cancellation remain bound to their original inference connection and authenticated actor; sharing the pending-work resource does not share a flow.

 Clearing chat caches retains these independent receipts. Saved connections → View cached history also shows their read-only management history after a credential is removed.

Controls use the verified stable [MCP routes and acknowledgements](https://github.com/NousResearch/hermes-agent/blob/bf0203a794a07aac3ff764972ab9087baa4e4f4e/hermes_cli/web_routers/mcp.py). A lost or malformed response and non-successful HTTP result remain uncertain; they are never treated as proof that no side effect occurred.

The used native-login and MCP control contracts were also rechecked against stable v0.22.6 (`f0d94882e89ab8d4098b5bb2f166adfb9ee0a0ab`). See the [source recheck](COMPATIBILITY.md#stable-v0226-source-recheck). Native renewal uses only tokens issued through this app’s native sign-in.

## Add an MCP server

After choosing a verified management profile, **Add MCP server** accepts either an HTTP/SSE URL or an executable on the Hermes host. HTTP servers support no authentication, a provisioned bearer credential, or OAuth configuration. Stdio servers accept up to 64 arguments (one per line, without shell quote processing) and 32 named environment values. These configure the host; the phone does not connect to that MCP URL or execute its command.

A separate review freezes the target and input before confirmation. It shows the dashboard/profile/actor, name, public URL or host command, auth mode and supplied variable names. URL query values and command arguments require explicit disclosure in that review. Bearer and environment values use password inputs and are not saved in instance state. Closing the form discards its local input; no provisioning request is made before confirmation.

New MCP configurations are enabled by the upstream create contract. The review states that they can load in new sessions. The client does not offer an ignored “create disabled” field. HTTP/SSE servers with OAuth or no existing authentication can use the reviewed native OAuth control described below. Connection testing remains a separate explicit action; accepted configuration is not proof that credentials or tools work.

Creation re-verifies identity and inventory, refuses an existing name rather than overwriting it, and claims the same durable management ledger before one request. Input arguments/environment maps are copied before review. Acknowledgement and readback must match the name, source, transport, enabled state and public connection fields; redacted credentials cannot be compared by value. The receipt contains only redacted mode/count/key metadata, never the provisioned token, URL, command, argument values or environment values. Lost replies and malformed acknowledgements remain uncertain and block a new attempt. No secret payload is retained for replay.

The used create fields and normalization/summary helpers are tracked in the active upstream compatibility baseline. Limits are deliberate mobile bounds: names 1–256 characters, URLs 8192, executable 512, arguments 64×2048, environment values 32×8192 and bearer credentials 16384. Unsupported URL userinfo, fragments, control characters and ambiguous backslashes are rejected locally.

## Catalog installation

**MCP catalog** reads the selected dashboard profile's catalog explicitly. Each entry includes its manifest description, source, transport, auth mode, command/arguments or URL, repository/ref, bootstrap commands, tool defaults and post-install notes. Selecting an installable entry opens those details with declared environment inputs, followed by a separate frozen target/profile/actor review. Environment values use password fields, stay transient and are omitted from durable receipts. Only manifest-declared names are accepted; required values must be supplied. Direct installations default to disabled until the user selects Enabled.

The app re-verifies identity, the complete reviewed catalog entry and absence of an existing MCP name before claiming the shared management receipt and sending once. A changed manifest or observed existing configuration refuses the write and requires a new review. This is a client preflight; the server has no revision/CAS contract preventing a concurrent external administrator from changing configuration between requests. Installing can execute host code or persist environment values before a later failure. Any lost, malformed or unsuccessful reply remains uncertain without automatic retry.

The pinned background clone/build route starts a host CLI action, ignores the requested enabled flag, and does not forward non-secret environment inputs to that command. The app therefore enables that path only for entries without declared environment inputs, states that the host's enabled default applies, and disables other background entries with a host-setup explanation. Unsupported transports are explained too. This is a verified backend contract limitation, not a working mobile credential workflow.

An exact name/mode acknowledgement records **accepted**, including whether work continues in the background. It never records installation completion. The returned action name identifies a catalog entry rather than a unique process attempt, so the app does not attach a guessed process result. Read configuration and test the connection separately; observations do not settle uncertain earlier work. Installed entries use the existing enable/remove/probe controls instead of an unreviewed reinstall. Use the separate MCP OAuth or Provider accounts controls for authorization.

Contracts: [stable catalog handlers](https://github.com/NousResearch/hermes-agent/blob/f0d94882e89ab8d4098b5bb2f166adfb9ee0a0ab/hermes_cli/web_routers/mcp.py), [installation behavior](https://github.com/NousResearch/hermes-agent/blob/f0d94882e89ab8d4098b5bb2f166adfb9ee0a0ab/hermes_cli/mcp_catalog.py). The compatibility baseline tracks catalog routes, request fields, manifest projection and installation/bootstrap helpers.

## MCP OAuth authorization

For eligible config-owned HTTP/SSE servers, **Authorize MCP OAuth** reviews the exact dashboard/profile/actor/server before starting one host flow. Stdio environment authentication, existing header credentials and plugin-owned servers use their respective setup controls. The Hermes host performs MCP discovery, registration, PKCE, callback validation and credential storage; the mobile app does not implement a provider SDK or obtain the MCP provider token.

The start request carries the explicit profile. Status and cancellation use only the returned opaque flow ID: those verified endpoints have no profile parameter or profile field in their snapshots. The app binds that ID to its original credential scope, dashboard, profile, actor and server in the durable receipt. It refuses another actor/profile/scope before reading or cancelling. Reopening the app can explicitly read the original flow without starting another. A lost start reply remains unknown; no flow ID is guessed and no start is replayed.

**Read authorization state** refreshes explicitly. A fresh authorization URL lives only in memory, never in Room, saved state or logs. **Open provider authorization** reviews the public destination without query values, then opens it in the external browser without app bearer headers/cookies. HTTPS is required in production. Changing context, closing management, starting a read or requesting cancellation clears retained URLs. Raw host errors and tool descriptions are discarded; only bounded names/counts and reported status are retained.

These are host-reported states, not authoritative agent execution outcomes. The same flow can reopen from approved/error to a new authorization attempt. The app therefore does not latch a terminal state, automatically open a URL, or automatically repeat the start. Reported approval does not prove that the gateway has reconnected. A missing/expired flow is shown as unavailable; it does not prove whether earlier credentials were saved. Use a separate MCP connection test to inspect current readiness.

**Cancel authorization flow** has its own target review and durable single-request receipt. A cancellation acknowledgement may still report approved/error; it does not revoke credentials already obtained or claim that all host work stopped. A missing flow can acknowledge expired. Unknown cancellation is retained without automatic retry. Cancellation controls are disabled while another resource mutation is uncertain; existing uncertainty can be reviewed separately.

The [stable OAuth routes](https://github.com/NousResearch/hermes-agent/blob/f0d94882e89ab8d4098b5bb2f166adfb9ee0a0ab/hermes_cli/web_routers/mcp.py), [flow lifecycle](https://github.com/NousResearch/hermes-agent/blob/f0d94882e89ab8d4098b5bb2f166adfb9ee0a0ab/tools/mcp_dashboard_oauth.py) and [host worker](https://github.com/NousResearch/hermes-agent/blob/f0d94882e89ab8d4098b5bb2f166adfb9ee0a0ab/hermes_cli/web_server_mcp.py) are tracked in the compatibility baseline. No database version change is needed; existing schema-9 management receipts retain the binding and redacted snapshots.

Management calls have a bounded 45-second read timeout and 60-second overall deadline, allowing the host OAuth handler's verified 30-second authorization-URL wait to return. Cancellation remains available; there is no connection retry or redirect following.

## Advanced schedule inventory

**Advanced schedules** reads the explicitly selected management profile's cron jobs and fresh details. This dashboard resource is separate from the inference API's jobs cache; the app does not infer that two listeners target the same host/profile. Each returned record must identify that exact profile. Blank or case/whitespace variants of the aggregate `all` selector are refused before any request. Duplicate job IDs and oversized inventories are refused rather than merged across profiles.

The list shows the reported schedule state and enabled flag; a missing flag stays unknown. Details include schedule/run timestamps, last host-reported status, prompt, selected runtime, skills/toolsets, script-only mode, host working directory, context sources, delivery, timezone/catch-up settings and repeat counters when supplied. Unlimited repeats require an explicit null count; absent or malformed counts are not interpreted as unlimited. These metadata views do not prove a successful execution or gateway readiness.

Detail buttons use the exact returned job ID. Unsupported/sentinel IDs have a visible explanation. Internal profile-home paths and raw run/delivery errors are not echoed into summaries; raw errors are replaced by an error-presence notice. Provider base URLs/credentials and internal profile-home paths are omitted from the displayed projection. Prompt/configuration values remain in memory for this view and are not added to Room or saved state. Switching API connection or management profile clears the view; old asynchronous responses cannot populate the new context.

The verified list endpoint returns a bare JSON array, while detail and existing management endpoints return objects. The shared client now supports both strict decoders with the same 2 MB bound, authentication, prefix, TLS, redirect and retry policies. Oversized replies direct the user to the host dashboard; no undocumented pagination or request fallback is attempted. Paused creation is described below. Existing-job mutation paths require their own verified strict profile scope.

Source: [profile-scoped cron routes](https://github.com/NousResearch/hermes-agent/blob/f0d94882e89ab8d4098b5bb2f166adfb9ee0a0ab/hermes_cli/web_routers/cron.py), [profile annotation](https://github.com/NousResearch/hermes-agent/blob/f0d94882e89ab8d4098b5bb2f166adfb9ee0a0ab/hermes_cli/web_server_cron.py), [stored job fields](https://github.com/NousResearch/hermes-agent/blob/f0d94882e89ab8d4098b5bb2f166adfb9ee0a0ab/cron/jobs.py).

## Create a paused advanced schedule

**Create paused schedule** first reads the management listener's authenticated OpenAPI document. It requires a declared string profile query and a creation body that explicitly accepts boolean `paused=true`, with the required schedule field. Every supplied field must be declared. A missing/disabled/incompatible document leaves creation unavailable with an explanation; schedule inspection remains available. This gate prevents older Pydantic bodies from silently ignoring an undeclared paused flag. It is a contract check, not a certification of an arbitrary deployment's implementation.

The typed form supports prompt/skills/script jobs, script-only mode, finite or unlimited repeats, configured home delivery targets, model/provider/base URL, job-context sources (including self continuity), an optional toolset allowlist, host working directory, IANA timezone, catch-up policy/window and pause reason. Basic repeats default to one; delivery defaults to saving on the Hermes host. A platform without a configured home destination is disabled. External delivery uses the selected profile's configured destination when the job runs, rather than pinning a recipient address. Script-only mode submits its script and omits unused agent fields.

An omitted toolset allowlist inherits profile settings. An explicit empty list remains an empty allowlist, including in saved details; it is never converted to inheritance or an unknown value. The grace range is 0–1440 minutes, with zero preserved, and applies only to cron cadences. Timezone, script existence/sandbox and directory validity are checked by Hermes. Paths refer to the host, not phone storage. Model/skill/tool identifiers are configuration requests, not proof of availability. Optional provider URLs can use host-side credentials and are reviewed with query values hidden until explicitly shown.

The review freezes dashboard/profile/actor and all selected inputs. Confirmation submits a literal `paused:true` body with the profile only in the query, as the verified create model declares. Immediately before the single POST, the app re-verifies identity, schema signature, current job names, selected context IDs and external target configuration. A known duplicate name is refused. These are client preflights; the server has no revision/idempotency contract preventing a concurrent external edit or duplicate.

The shared durable receipt is claimed before transmission and keeps only field names/counts and redacted outcome metadata. The full prompt, provider URL, script, working directory and body are not saved in a mobile receipt or replay file. Acknowledgements must identify the requested name/profile and an addressable job, paused/disabled with no next run and zero completed repeats. Fresh readback checks the same job and configuration. Normalized schedule/path interpretation is inspected while paused; a valid acknowledgement is retained when later configuration validation/readback fails. Configuration acceptance is separate from execution success and activation.

Lost, malformed or unsuccessful replies and interrupted sends remain uncertain without automatic retry. **Read current configuration** on a cron receipt reads that profile's cron inventory; it never queries an MCP server with the job's name and never settles uncertainty automatically. Clearing chat caches keeps the independent receipt. Relative scripts must stay within the selected profile's scripts directory. The normal paused-create path returns before first scheduler registration; other partial post-save failures still cannot be assumed side-effect-free.

Creation supports the declared dashboard `CronJobCreate` fields. CLI-only monitor scripts/URLs, interpreter, reasoning pins, failure delivery and session attachment are not sent as ignored creation options. Any later support must use separately verified update contracts. Mobile bounds include 160-character names, 512-character schedule expressions, 5000-character prompts, 1–1000000 finite repeats, 64 entries per list, 1024-character relative script paths, 2048-character directories and 8192-character provider URLs.

## Installed skill controls

**Installed skill controls** reads the selected management profile's skill inventory, including disabled skills. It shows names, descriptions, provenance, availability and curator edit locks. Missing flags remain unknown and their controls are disabled with an explanation; string/numeric flags and duplicate identities are refused. The current projection is limited to 1000 skills. Aggregate/ambient selectors are not accepted for these requests.

**Read SKILL.md** requests the exact name as an encoded query value. The returned name must match; content is bounded to 131072 characters and displayed as plain text without executing instructions or loading linked resources. Host paths from the response are omitted. Skill content is ephemeral view state, cleared on connection/profile changes, and is not put into Room, saved instance state or action receipts.

Enable/disable and curator lock/unlock use a separate review of the exact dashboard, profile, actor, skill and effect. Disabling changes profile availability for future prompt loading; it is not file removal, tool authorization or a stop request. Hermes ignores disable requests for its essential `hermes-agent` skill, so that control is disabled with a reason. Curator locks govern autonomous curator/background-review edits; user edits remain allowed. They are not general filesystem permissions or a guarantee against arbitrary host code writing files.

Before one PUT, the app re-verifies identity and reads the typed inventory. Any change to the reviewed name/description/provenance/availability/lock refuses the write. The profile appears consistently in the query and body. The shared durable management ledger is claimed before transmission and stores only the target and requested boolean. Acknowledgements require exact name, boolean and `ok:true`. Fresh inventory readback is separate; failure cannot erase an acknowledgement. There is no revision/CAS contract against concurrent host edits, no immutable content identity in these name-based controls, and no automatic retry of an unknown result.

Skill receipts' **Read current configuration** reads skills, never an MCP server with the same name, and does not settle uncertainty or assert execution success. Clearing chat caches retains these receipts. The current chunk does not install/uninstall/update hub bundles or edit skill files; those need their own source/content review and accepted-background-work handling.

## Gateway schedules

**Gateway schedules → Read gateway schedules** reviews the dashboard URL, explicit management profile, actor and connection effect before opening anything. Gateway connection can initialize the host's configured MCP processes; the review states this. Opening the dialog alone does not mint a ticket or connect. This is an independent gateway view, separate from inference jobs and the richer dashboard cron details.

The native management bearer mints one 30-second single-use ticket through `POST /api/auth/ws-ticket`. The app sends that ticket only in the documented gateway subprotocol header for the same prefixed origin's `/api/ws`; the WebSocket receives no standing bearer, cookie, credential-bearing query or invented native grant. It requires the selected public `hermes-gateway-v1` protocol and `gateway.ready` event, then sends one `cron.manage` request with an explicit profile, `action:list` and `include_disabled:true`. The returned `scoped` string must exactly match the reviewed profile; missing/mismatched proof, malformed flags/counts and duplicate IDs are rejected. The legacy `hermes`/`.hermes` profile aliases are disabled (including case variants): upstream can map a missing alias to `default` while echoing the requested string, which is insufficient proof for these profiles.

Socket/RPC replies use exact string request IDs, JSON-RPC 2.0 and a single result/error shape. Raw error messages, ready-event skin data, host paths, provider URLs and job errors are not reflected into summaries. Public name/schedule/state, enabled flag, next run, last reported status and clearly labelled prompt preview are shown. Scheduler readiness remains reported/unknown rather than proof that a job ran. Missing enabled flags stay unknown. Inventory is bounded to 500 rows/65536 serialized characters per row; inbound messages are rejected after receipt above 2 MB, with an 8 MB cumulative processing bound and at most 256 ignored event notifications. OkHttp buffers WebSocket messages before the listener checks these bounds; this is not a streaming memory-limit claim.

The connection has bounded open/ready/RPC waits, closes after the explicit read or cancellation, and never reconnects or retries. A rejected ticket is not reused and does not trigger a fallback to a standing token in the URL. No server-request capability, transcript subscription, session creation or agent turn is sent. Current data is transient and discarded on connection/profile changes; generation guards reject late results.

The dashboard's existing-job mutation route can fall back across profiles when its ownership hint misses, so those mutations are not used. Source review found a separate `cron.manage` profile resolver that refuses missing named profiles; its legacy aliases are disabled as described above. The supported controls below use that RPC scope. Advanced update/trigger/cancel are not exposed through this contract.

## Reviewed gateway schedule controls

The gateway view offers **Pause**, **Resume** and **Remove schedule and outputs** only for supported, addressable records. Each action opens its own frozen dashboard/profile/actor/ID/configuration review. A known enabled flag is required for pause; resume requires a known disabled/paused record. Unknown states and unsupported IDs have explanations. A known second job name matching the selected ID disables these controls to avoid the host's ID/name fallback ambiguity. An unresolved management write blocks further writes on that same resource, across MCP, skills and cron.

| Action | Acknowledged configuration/effect | What it does not prove |
| --- | --- | --- |
| Pause | Disables future scheduling | A current run may continue; this does not request cancellation |
| Resume | Enables the stored job; an overdue recurring slot can fire under host catch-up policy | Scheduler/provider/delivery readiness or successful execution |
| Remove | Removes the job, its saved output directory and notepad; requests cooperative cancellation of its live run | Immediate cessation of execution or restoration of deleted output |

The review shows the gateway's **prompt preview**, reported runtime/delivery/script/context fields and toolset metadata. It does not present a 100-character upstream preview as the full prompt. The upstream projection can omit an explicitly empty toolset allowlist, so omission is labelled unreported rather than inherited; use **Advanced schedules** for the full dashboard configuration. Reported empty lists stay empty. Provider/monitor URL userinfo is always omitted, query values are hidden until explicitly shown, and no URL is fetched by the phone. These values remain transient and are not added to action receipts.

Confirmation re-verifies the management identity, opens one fresh ticket-authenticated connection and reads a profile-proven inventory including disabled jobs. It compares the immutable reviewed public configuration and refuses a changed record or known ID/name collision before claiming a receipt. A deletion already observed absent returns an observation without another write or a new receipt. The same socket then carries one supported `cron.manage` action with only `action`, `name` (the selected ID) and explicit `profile`. No unsupported strict/revision/idempotency field is invented.

Hermes resolves an exact ID first, then a case-insensitive matching name when that ID is absent. The app refuses known collisions, but the server has no compare-and-swap contract preventing another administrator from deleting/replacing/renaming jobs after the preflight. The review states this limitation; the app does not claim atomic immutable instance identity. The request is always scoped to its reviewed non-alias profile. Acknowledgements must report typed success and the exact selected job ID/name plus desired enabled state, or exact removed ID/name. The app claims the common durable management ledger before this single mutation. A receipt stores only the target ID, action/previous enabled flag and redacted acknowledgement, never prompt previews, URL values, scripts, tokens or configuration hashes.
