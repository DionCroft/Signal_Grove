# Keeping the companion current with Hermes

The active [contract baseline](contracts/hermes-baseline.json) describes the implemented mobile client, reviewed against Hermes v0.22.6 (`f0d94882e89ab8d4098b5bb2f166adfb9ee0a0ab`). It currently tracks 32 inference API routes, 38 dashboard management routes (including the WebSocket), 451 handler/normalizer/protocol-constant AST fingerprints and 170 management/RPC typed fields, plus used static flags and cron limits/fields. The checkpoints below retain their historical counts. Skill source tracking includes the essential-skill exclusion, catalog projection, disabled-skill configuration and curator lock persistence. A changed essential set requires review before mobile controls are updated. The historical [2026-11-02 audit](audits/2026-11-02/REPORT.md) remains unchanged; its four confirmed mobile defects have been fixed and are not represented as open in the active baseline.

The **Hermes compatibility** GitHub workflow runs weekly on Monday at 07:27 UTC, on relevant source/baseline changes, and through manual dispatch. It checks latest stable and main separately. It reads public GitHub source at one resolved commit, parses it as data and never imports or executes Hermes. It sends no deployment credentials and performs no server mutation. PRs run the offline parser tests without the live-source job. Results and additions are retained in workflow artifacts; used-contract changes fail their check for review. Module hashes also expose changes outside the explicitly tracked handlers. New routes and features require triage even when existing used contracts remain unchanged. No baseline or dependency is updated automatically.

Local commands (Python 3.10+ and authenticated GitHub CLI):

```text
python -B -m unittest discover -s scripts/tests -v
python -B scripts/check_hermes_contract.py --ref latest
python -B scripts/check_hermes_contract.py --ref main
```

On the owner’s Windows machine, set TEMP/TMP to E: before invoking tools and keep output files there. `--output` saves JSON; `--baseline` selects historical evidence; `--snapshot-only` emits a source snapshot. Exit 0 means no change to this tracked surface, 2 means used-contract review is required, and 3 means inspection was incomplete. A passing check is not live interoperability or security certification. Transitive helpers, provider behavior, deployed configuration, runtime gates, auth policies and hardware/OEM behavior still need review and their actual environments.

Before accepting a changed baseline, review the source/payload and pre-mutation guards, adjust the client and meaningful regressions as needed, and rerun local checks. Replace the baseline’s `upstream` section only with the reviewed snapshot, preserve the used lists and extend them for newly implemented routes/fields/handlers. Record the reviewed commit/date and rerun stable/main. Do not copy an entire new baseline merely to clear a failing check. AST fingerprints ignore comments, top-level handler docstrings, locations and optional empty fields; changed executable bodies and field types remain visible.

The Android workflow builds, runs JVM tests/lint and compiles instrumentation, then supplies both APKs to separate API 26/37 Linux device jobs. Each job creates its own fresh Google APIs x86_64 emulator in runner temporary storage, uses KVM and a software renderer, verifies the actual API, and runs the complete unfiltered instrumentation suite. API 26 uses 130% font scale. API 37 starts with local-network permission revoked so the real deny/grant test remains meaningful. A missing emulator, timeout, failed instrumentation marker or absence of a positive test result fails the job; it never falls back to another API or claims a compile as device execution.

Only test/emulator/SDK logs and fixture screenshots are retained for seven days; AVD disks, app data and Android user-home directories are excluded. Device jobs use the already verified APK artifacts and no deployment credentials. The Python helper refuses non-GitHub/non-Linux environments to avoid touching an owner's existing devices. Windows tools and local test data continue to use E:. Each hosted result is recorded in [VALIDATION.md](VALIDATION.md); configuration or APK compilation alone never counts as device execution. Dependency integrity is enforced as described below; vulnerability review remains a separate check. Source checks complement device tests and cannot replace them.

Primary references: [Android emulator command line](https://developer.android.com/studio/run/emulator-commandline), [hardware acceleration](https://developer.android.com/studio/run/emulator-acceleration), [GitHub-hosted Linux acceleration](https://docs.github.com/en/actions/reference/runners/github-hosted-runners).

Workflow scheduling follows the [GitHub Actions schedule contract](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule); repository Actions must remain enabled.

## Dependency integrity

The committed `gradle/verification-metadata.xml` records SHA-256 for 1071 artifacts across 495 resolved components, including plugin/build/test dependencies and POM/module metadata. Strict Gradle verification is the default when this file exists and is explicit in CI and the Windows build entry point. CI also runs the policy checker and its negative regressions, refusing disabled metadata verification, blanket artifact trust, missing/placeholder hashes and duplicate identities. The pinned Gradle setup action validates wrapper jars by default; the wrapper distribution already has its own SHA-256 pin.

The initial file was generated from the existing trusted build cache with Gradle's checksum bootstrapping, then reviewed for explicit hashes and absence of trust bypasses. This is trust on first use, not proof that dependencies are free of vulnerabilities or malicious code. The Windows aapt2 artifact was checked against the canonical Google Maven HTTPS download; Linux/macOS aapt2 hashes were added from the same pinned Google Maven component so another platform does not need an unverified build. Windows execution is locally verified, and the strict Linux build plus fresh API 26/37 device matrix passed in [hosted CI](https://github.com/DionCroft/hermes-agent-android/actions/runs/41527686477). macOS build execution remains unverified.

Do not bootstrap verification metadata during an ordinary CI build, disable verification to fix a failure, or accept a changed binary's checksum without reviewing its source/version and publisher distribution. For an intentional dependency change, generate additions locally, inspect every coordinate/artifact/hash diff, verify important publisher artifacts, and run the strict build again. Missing platform variants must be reviewed explicitly. Metadata, artifact and wrapper verification complement vulnerability review; they do not replace it.

Local policy check: `python -B scripts/check_verification_policy.py`. Gradle update option: `--write-verification-metadata sha256`; validation option: `--dependency-verification strict`. Keep all owner-machine temporary downloads/canaries on E:. An isolated canary with a deliberately wrong checksum failed strict artifact resolution, then passed with the original checksum restored; neither production metadata nor cached binaries were tampered with.

Primary behavior: [Gradle dependency verification](https://docs.gradle.org/current/userguide/dependency_verification.html), [pinned setup action wrapper validation](https://github.com/gradle/actions/blob/ed408507eac070d1f99cc633dbcf757c94c7933a/setup-gradle/action.yml).

### Verified public-source cache

Compatibility CI now uses optional `--source-cache` under its isolated runner temp directory. On Windows, put this cache on E: with other task temporary data. The CLI/library remain uncached when that option is omitted. Every cached run resolves the requested upstream ref afresh and fetches its exact commit's recursive Git tree. A CLI JSON projection retains only the watched paths and identity fields while preserving the tree's completeness flag; the existing 3 MB response bound is unchanged. A missing/truncated/ambiguous tree, symlink/submodule/non-file entry, invalid blob identity or oversized source refuses inspection. The [official Git tree contract](https://docs.github.com/en/rest/git/trees#get-a-tree) defines those identity/mode/completeness fields.

The cache contains only public upstream UTF-8 source blobs, named by Git blob SHA-1. Each read and new download must match the fresh tree's exact byte length and Git blob identity, inside the existing 2 MB file limit. Symlink/non-regular targets, corrupt bytes and invalid UTF-8 fail closed without a redownload to hide the failure. New entries publish atomically only after verification; failed publication leaves no partial cache file. Tree/ref access still needs GitHub: a 429/permission failure cannot be satisfied by an old cached snapshot. Existing pacing, queued-failure cancellation, selected 5xx raw-representation fallback, baseline comparison and exact reviewed variants are unchanged. Git object identity is consistency evidence within the existing upstream trust model, not independent publisher/runtime attestation.

The workflow uses separate [official actions/cache v6.1.0 restore/save actions](https://github.com/actions/cache/tree/55cc8345863c7cc4c66a329aec7e433d2d1c52a9), pinned to that complete commit. A common public-blob cache is shared by stable and main. Both checks run sequentially in one job; main retains the default success condition and is skipped if stable fails or is incomplete. The job remains failed. Before retaining any cache, an always-run local check requires a nonempty directory of at most 512 ordinary, non-symlink, Git-hash-named UTF-8 blobs, each inside 2 MB and 128 MB total, with every filename matching its bytes. Valid partial blobs can be saved after a failed source inspection, so the next independent run can reuse completed downloads; corrupt/unexpected/incomplete cache entries prevent publication. Cache retention never makes a failed compatibility result pass. Every later read still needs fresh upstream ref/tree identities and verifies each selected blob before AST comparison. Existing artifacts keep their stable/main names, now containing separate per-ref JSON files. Read-only workflow permissions and rate-refusal/no-retry behavior are unchanged. GitHub documents [rate limits and diagnostics](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api); prior 429 logs alone do not establish which limit was reached.
